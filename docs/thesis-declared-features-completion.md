## 2. Задачи (astrakhan-admin)

### 2.1. Автоматизация публикации по `publishAt` / `unpublishAt`

**Приоритет:** высокий  
**Соответствие тезису:** «Планирование, назначение даты и времени автоматической публикации или снятия с публикации».

**Текущее состояние:** `PointOfInterest.publishAt`, `unpublishAt`; форма `templates/poi/form.html`. Публичный список: `PoiService.findPublished()` только по `status = PUBLISHED`, даты не учитываются. Фоновых задач нет.

**Предлагаемая реализация:**

1. Включить планировщик Spring: `@EnableScheduling` в конфигурации (например отдельный `SchedulingConfig.java`).
2. Компонент `PoiPublicationScheduler` (или `ScheduledPublicationService`):
   - cron каждые 1–5 минут;
   - для записей со `status` ∈ {`DRAFT`, `PENDING`} и `publishAt <= now` → выставить `PUBLISHED`;
   - для записей со `status = PUBLISHED` и `unpublishAt != null` и `unpublishAt <= now` → `ARCHIVED` (или `DRAFT` — зафиксировать одно правило в коде и в записке).
3. Публичный API (`ApiController.getPois`, `getPoi`): отдавать только ТОИ, которые **сейчас** должны быть видны посетителю:
   - `status = PUBLISHED`;
   - и `(publishAt IS NULL OR publishAt <= now)`;
   - и `(unpublishAt IS NULL OR unpublishAt > now)`.
4. Вынести общую логику «видим ли POI гостю» в `PoiService` (например `isPubliclyVisible(PointOfInterest, LocalDateTime now)`), чтобы не дублировать в API и при необходимости в планировщике.

**Файлы (ориентир):**

- `astrakhan-admin/src/main/java/ru/astrakhan/admin/entity/PointOfInterest.java`
- `astrakhan-admin/src/main/java/ru/astrakhan/admin/service/PoiService.java`
- `astrakhan-admin/src/main/java/ru/astrakhan/admin/repository/PoiRepository.java` — при необходимости `@Query` для выборки кандидатов на публикацию/снятие
- `astrakhan-admin/src/main/java/ru/astrakhan/admin/controller/ApiController.java`
- Новый: `.../config/SchedulingConfig.java`, `.../scheduler/PoiPublicationScheduler.java` (или сервис + `@Scheduled`)

**Критерии приёмки:**

- После наступления `publishAt` ТОИ сама становится опубликованной без ручного нажатия (в пределах интервала cron).
- После наступления `unpublishAt` ТОИ исчезает из `/api/v1/pois` для гостей.
- В админке список «все ТОИ» по-прежнему показывает черновики по бизнес-правилам UI (не смешивать с гостевой выдачей).

### 2.2. AI: помощь в описании ТОИ и адаптация под возраст (в панели сотрудника)

**Приоритет:** высокий  
**Соответствие тезису:** «Использование AI-моделей: помощь в создании описаний точек интереса, адаптация текста под разные возрастные группы».

**Текущее состояние:** генерация есть на стороне `module2/server` (`/api/node/ai/generate`, аудитории `default` | `children` | `academic`). В админке отсутствует.

**Предлагаемая реализация (вариант A — предпочтительный):**

- В `astrakhan-admin` добавить сервис вызова LLM через HTTP (например `WebClient` / `RestClient`) к API совместимому с OpenAI chat completions **или** к Groq, как в module2.
- Конфигурация только на сервере: `app.ai.enabled`, `app.ai.api-key` (env), `app.ai.base-url`, `app.ai.model` в `application.properties` / prod.
- Эндпоинт для админки (только для ролей с доступом к ТОИ), например `POST /admin/api/poi/ai-description` с телом `{ "name", "category", "description", "foundedYear", "architect", ... , "audience": "default|children|academic" }` → возвращает `{ "text": "..." }`.
- В `poi/form.html`: кнопка «Сгенерировать описание», выпадающий список аудитории, вставка результата в textarea описания (с подтверждением перезаписи).

**Безопасность:** ключ не на клиенте; CSRF для форм админки; rate limit по IP/пользователю (опционально, `GuestOrderLookupService` можно взять за образец идеи лимитов).

**Файлы (ориентир):**

- Новый: `service/PoiAiDescriptionService.java`, `controller/PoiAiController.java` (или методы в `PoiAdminController`)
- `application.properties`, `application-prod.properties`
- `templates/poi/form.html` + небольшой JS (или Thymeleaf + fetch с CSRF-токеном из существующего layout)

**Критерии приёмки:**

- Сотрудник из админки получает черновик описания по метаданным ТОИ для трёх режимов аудитории.
- При выключенном `app.ai.enabled` UI показывает понятное сообщение, без падения страницы.

### 2.3. Автоматическое описание и тегирование загружаемых изображений ТОИ

**Приоритет:** средний (сложность выше остальных)  
**Соответствие тезису:** «Автоматические описание и тегирование загружаемых изображений».

**Текущее состояние:** загрузка файла в ТОИ; теги и описание только вручную.

**Варианты:**

| Вариант | Суть | Плюсы / минусы |
|--------|------|----------------|
| **B1. Vision API** | После загрузки изображения вызов мультимодальной модели (OpenAI/Groq/Yandex и т.д.) → JSON: краткий alt-текст + список тегов | Максимально близко к тезису; нужны ключи, лимиты, обработка ошибок |
| **B2. MVP без vision** | Кнопка «Предложить теги из названия и категории» (эвристика + тот же LLM только по тексту) | Быстрее внедрить; формально слабее отвечает формулировке «изображений» |
| **B3. Отложено** | В записке указать как этап 2 после защиты | Если нет времени на B1 |

**Рекомендация для диплома:** реализовать **B1** в упрощённом виде: один запрос vision, дописать поля `imageAlt` / дополнение к `tags` (не перетирать вручную введённые без подтверждения).

**Файлы (ориентир):** `PoiAdminController` (обработка multipart), новый `PoiImageAnalysisService`, сущность при необходимости новые поля или только merge в `description`/`tags` по согласованию.

**Критерии приёмки:**

- После загрузки фото оператор может нажать «Проанализировать изображение» и получить предложение тегов/подписи.
- Ошибки API не ломают сохранение ТОИ.

### 2.4. Уведомления пользователям о новых метках на карте или событиях

**Приоритет:** средний  
**Соответствие тезису:** «Отправка уведомлений о новых метках на карте или событиях».

**Текущее состояние:** `OrderEmailService` — заказы; массовых уведомлений о ТОИ нет.

**Предлагаемая реализация (минимальный жизнеспособный продукт):**

1. Таблица подписчиков, например `news_subscribers`: `email`, `subscribed_at`, `active`, опционально `confirm_token` (если нужен double opt-in).
2. Сбор подписки:
   - чекбокс в форме оформления заказа / контактной форме module2 **или** отдельная форма «Подписаться на новости»;
   - API в `ApiController`: `POST /api/v1/newsletter/subscribe` с валидацией email.
3. При переходе ТОИ в **первую** публикацию (`PUBLISHED` впервые) или при явной кнопке в админке «Разослать уведомление о точке»:
   - асинхронная рассылка через существующий `JavaMailSender` (паттерн как в `OrderEmailService`);
   - шаблон письма: название ТОИ, краткое описание, ссылка на карту (base URL из `app.module2.url` или отдельное свойство).
4. Для «событий»: либо отдельная сущность `Event` + та же рассылка, либо в MVP трактовать «событие» как публикацию нового маршрута/новости — зафиксировать в записке один сценарий.

**Файлы (ориентир):**

- Новый: entity + repository + `NewsletterService` / `PoiPublishedNotificationService`
- `OrderEmailService` или общий `MailNotificationService` для переиспользования отправки HTML
- `PoiService.publish` / планировщик из п. 2.1 — hook «после первого перехода в PUBLISHED»
- module2: чекбокс + вызов API (если подписка с витрины)

**Критерии приёмки:**

- Подписчик получает письмо при появлении новой опубликованной ТОИ (по выбранному правилу: автоматически или по кнопке админа).
- Отписка (ссылка в письме) желательна для юридической аккуратности (`/api/v1/newsletter/unsubscribe?token=`).

**Связь с п. 3.2:** письмо и модалка на сайте дополняют друг друга: одно для подписчиков по email, второе — для активных посетителей карты без подписки.

### 2.7. Telegram как канал подтверждения и уведомлений по заказу

**Приоритет:** высокий  
**Соответствие тезису:** надёжная доставка пользовательских уведомлений при недоступной почте.

**Текущее состояние:** подтверждение просмотра заказов и уведомления о статусах заказа завязаны на email (`GuestOrderLookupService`, `OrderEmailService`).

**Предлагаемая реализация (MVP):**

1. Добавить сценарий привязки Telegram через deep-link:
   - фронт запрашивает `link token`,
   - пользователь открывает `https://t.me/<bot>?start=link_<token>`,
   - бот подтверждает токен во внутреннем API Java.
2. Хранить связь `telegram_chat_id <-> пользователь/контакт` в БД (`user_telegram_links`) + таблицу одноразовых токенов (`telegram_link_tokens`).
3. При смене статуса заказа в `OrderAdminController` отправлять уведомление в Telegram:
   - минимум: `SHIPPED` + трек-номер,
   - далее: `PROCESSING`, `DELIVERED`, `CANCELLED`.
4. Оставить email как fallback, но Telegram сделать приоритетным каналом, если привязка активна.

**Файлы (ориентир):**

- `astrakhan-admin/src/main/java/.../controller/ApiController.java` (API привязки/статуса Telegram)
- `astrakhan-admin/src/main/java/.../controller/OrderAdminController.java` (триггер отправки уведомления)
- `astrakhan-admin/src/main/java/.../service/GuestOrderLookupService.java` (альтернативный канал подтверждения)
- `module2/src/views/OrdersView.vue`, `module2/src/api/backend.js` (UI и API-клиент привязки)
- `module3/telegram_bot.py` (обработчик `/start link_<token>` и отправка статусов)

**Критерии приёмки:**

- Пользователь может привязать Telegram без email.
- После изменения статуса заказа сообщение приходит в Telegram.
- При недоступной почте критичные уведомления не теряются.
- Секреты бота и service-token вынесены в env, хардкод-токены удалены/ротированы.

### 3.2. Запросы к API и модалка «Новая точка на карте» у клиента

**Приоритет:** средний  
**Соответствие тезису:** «Уведомления пользователям о новых метках на карте» — вариант **внутри веб-приложения** (без email): пользователь на витрине периодически узнаёт о появлении новых опубликованных ТОИ и видит модальное окно.

**Текущее состояние:** клиент подгружает список ТОИ при заходе на карту (`fetchPois`); фоновой проверки «появилось ли что-то новое после моего последнего визита» нет.

**Предлагаемая реализация:**

1. **Бэкенд (`astrakhan-admin`, публичный API в `ApiController`):**
   - Эндпоинт с **лёгким ответом**, например:
     - `GET /api/v1/pois/since?afterId={long}` — вернуть ТОИ с `id > afterId`, видимые гостю (те же правила, что в п. 2.1: `PUBLISHED`, учёт `publishAt` / `unpublishAt`), лимит N (например 5–10), поля минимум: `id`, `name`, `category`, опционально короткий `description`, координаты для кнопки «Показать на карте»;
     - или `GET /api/v1/pois/since?updatedAfter={ISO-8601}` — если удобнее ориентироваться на `updatedAt` (нужен индекс/запрос по времени).
   - Альтернатива/дополнение: `GET /api/v1/pois/catalog-revision` → одно число (версия или max `id` каталога), клиент сравнивает с сохранённым значением и только при изменении запрашивает детали — меньше трафика.

2. **Клиент (`module2`):**
   - Периодический **polling** (например каждые 45–90 с) пока открыта вкладка с приложением или только на маршруте карты (`MapView.vue`) / глобально в `App.vue` — зафиксировать в записке.
   - В `localStorage` хранить последний известный **`max(id)`** или `catalogRevision`, чтобы после перезагрузки не показывать старые точки повторно; отдельный Set/список `dismissedPoiIds` для точек, которые пользователь закрыл в модалке без перехода.
   - При наличии новых записей — показать **модалку** (PrimeVue `Dialog` или существующий паттерн проекта): заголовок вроде «На карте новая точка», название, 1–2 предложения, кнопки «Открыть на карте» (фокус на ТОИ + `mapStore.fetchPois()` / выбор POI) и «Закрыть».
   - Не дублировать модалку для одного и того же `id` в рамках сессии.

3. **Что не требуется для MVP:** WebSocket/SSE; при необходимости вынести в «этап 2».

**Файлы (ориентир):**

- `astrakhan-admin/.../controller/ApiController.java` — новые методы + переиспользование фильтра видимости из `PoiService`
- `astrakhan-admin/.../service/PoiService.java` — метод `findPublishedVisibleAfterId(long afterId, int limit)` или аналог
- `module2/src/views/MapView.vue` и/или `module2/src/App.vue` — интервал, модалка, работа с `localStorage`
- `module2/src/store/index.js` (map store) — при необходимости экшен «показать POI по id после refresh списка»

**Критерии приёмки:**

- После публикации новой ТОИ в админке у пользователя с открытой витриной в течение интервала polling появляется модалка (или после следующего захода на карту — если polling только на `MapView`).
- Повторно та же точка не показывается после закрытия/подтверждения (по правилам `localStorage`).
- Эндпоинт не отдаёт черновики и не нарушает правила видимости по датам из п. 2.1.

## 4. Рекомендуемый порядок внедрения
