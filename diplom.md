## Часть I. Система и архитектура

## 1. Общая характеристика системы

Проект `Astra-microfront` реализует цифровую экосистему для историко-туристического сервиса:

- пользовательский интерфейс (`module2`) для гостей и клиентов;
- административный контур контента и заказов (`astrakhan-admin`);
- техническая админка и аналитика (`module3`).

Ключевая цель реализации: объединить пользовательский путь (маршруты, заказы, геймификация) с операционным управлением и мониторингом качества данных.

## 4. API-спецификация (черновик раздела “Контракты API”)

### 4.1. Прогресс пользователя

`GET /api/v1/user-progress?email={email}`

- назначение: получить snapshot прогресса;
- ответ: `email`, `snapshot`, `updatedAt`.

`POST /api/v1/user-progress/sync`

- назначение: сохранить snapshot прогресса;
- тело: `email`, `snapshot`;
- ответ: `email`, `snapshot`, `updatedAt`.

`GET /api/v1/user-progress/confirmed?email={email}`

- назначение: получить подтвержденные сервером счетчики;
- ответ:
  - `completedPaidRoutes`
  - `completedFreeRoutes`
  - `completedRoutes`
  - `earnedRewards`
  - `usedRewards`
  - `availableRewards`

### 4.2. Маршруты и награды

`POST /api/v1/routes/{id}/complete`

- назначение: зафиксировать прохождение маршрута;
- тело: `email`;
- результат: обновленные подтвержденные счетчики.

`POST /api/v1/rewards/redeem`

- назначение: списать награду на платный маршрут;
- тело: `email`, `routeId`;
- валидации:
  - маршрут существует,
  - маршрут платный,
  - у пользователя есть доступные награды.

### 4.3. Заказы

В объектах заказа добавлены поля:

- `orderType: "paid" | "free"`
- `routeType: "paid" | "free"`

Использование: строгая серверно-ориентированная фильтрация заказов в ЛК.

### 4.4. Технические метрики

`GET /api/metrics/activity`  
`GET /api/metrics/daily`  
`GET /api/metrics/ops`  
`GET /api/metrics/funnel`  
`GET /api/metrics/data-quality`  
`GET /api/metrics/alerts`

## 5. Данные для диаграмм последовательностей (Sequence)

### 5.1. Вход в ЛК и синхронизация

1. Пользователь запрашивает код на email.
2. Пользователь подтверждает код.
3. `module2` получает заказы.
4. `module2` получает серверный snapshot прогресса.
5. Выполняется merge local/server.
6. Выполняется sync обновленного snapshot на сервер.

### 5.2. Подтверждение прохождения маршрута

1. Пользователь нажимает “Отметить как пройденный”.
2. `module2` отправляет `POST /routes/{id}/complete`.
3. Backend сохраняет событие (с дедупликацией по email+route).
4. Backend возвращает подтвержденные счетчики.
5. UI обновляет прогресс.

### 5.3. Применение награды на платный маршрут

1. Пользователь выбирает платный маршрут.
2. `module2` запрашивает confirmed progress.
3. Если `availableRewards > 0`, отправляется `POST /rewards/redeem`.
4. Backend фиксирует списание награды.
5. Пользователь получает доступ к маршруту без оплаты в рамках reward-flow.

## 11. Полное описание функционала `module2` (для раздела диплома)

Раздел описывает пользовательский модуль как законченный продуктовый контур: от карты и маршрутов до заказа и личного кабинета.

### 11.1. Главная карта и работа с POI

Витрина `module2` построена вокруг интерактивной карты и сценариев исследования города.

Что реализовано:

- отображение POI из публичного Java API;
- открытие карточки точки:
  - название, категория, описание,
  - расширенные поля (контакты, сайт, теги, доп. сведения);
- поддержка “следования маршруту” на карте:
  - выбор маршрута,
  - построение последовательности точек,
  - баннер активного маршрута;
- определение и отображение геопозиции пользователя (при разрешении браузера);
- контроль появления новых POI:
  - polling ревизии каталога,
  - логика “новая точка” с пользовательским подтверждением;
- модалка предложения новой точки:
  - пользователь отправляет предложение прямо из карты.

Практическая ценность для диплома:

- демонстрация data-driven UI (данные из API);
- демонстрация обработки асинхронных обновлений каталога;
- демонстрация пользовательского генеративного сценария (предложение контента).

### 11.2. AI и мультимедийные функции

Реализованы вспомогательные AI-функции в пользовательском контуре:

- генерация описаний POI в разных режимах аудитории (`default/children/academic`);
- озвучивание текста (TTS);
- проксирование AI-запросов через backend-слой для защиты ключей.

### 11.3. Маршруты

Каталог маршрутов реализует:

- фильтрацию по категории, по типу (`free/paid`), по избранному;
- карточки маршрутов с метаданными и стоимостью;
- модальное окно маршрута:
  - подробное описание,
  - список остановок,
  - старт маршрута;
- share-функционал:
  - Web Share API (где доступно),
  - fallback-модалка со ссылкой,
  - генерация QR.

Дополнительно в рамках расширений диплома:

- фиксация прохождения маршрута (подтвержденное событие);
- использование награды для конкретного платного маршрута.

### 11.4. Магазин и checkout

Товарный контур в `module2` включает:

- каталог товаров с фильтрацией и сортировкой;
- карточку товара, варианты/количество;
- корзину с управлением позициями;
- checkout-форму клиента (доставка, контактные данные, метод оплаты);
- создание заказа через Java API;
- сценарий оплаты:
  - генерация payment link,
  - обработка успешного возврата,
  - fallback-сценарий при недоступной кассе.

### 11.5. Личный кабинет заказов

Реализован гостевой кабинет с усиленной безопасностью:

- вход по email + одноразовому коду;
- контроль Telegram-привязки;
- просмотр истории заказов с группировкой и фильтрами;
- таймлайн статусов заказа;
- отображение состава заказа.

### 11.6. Геймификация и прогресс пользователя

В рамках проекта реализована прикладная геймификация:

- подсчет посещенных точек и пройденных маршрутов;
- достижения (ачивки) и прогресс по ним;
- награды за комбинацию активностей;
- история активности;
- синхронизация прогресса с сервером (этап 2);
- подтвержденные серверные счетчики прохождений;
- списание награды на конкретный платный маршрут.

### 11.7. Техническая организация `module2`

- композиционная архитектура на `views/components/composables/store`;
- API-слой вынесен в `module2/src/api/backend.js`;
- важные пользовательские состояния дублируются:
  - локально (быстрый UX),
  - серверно (подтвержденные бизнес-события).

## 12. Полное описание функционала `astrakhan-admin`

`astrakhan-admin` является центральным бизнес-модулем: хранит данные, управляет публикациями, предоставляет публичный API и внутренние контуры операторской работы.

### 12.1. Управление контентом

Сущности:

- POI (точки интереса),
- Routes (маршруты),
- Products (товары),
- Feedback / POI Suggestions (обратная связь и предложения).

Реализованные возможности:

- создание/редактирование/публикация;
- загрузка и хранение медиа;
- поля публикации и статусов;
- AI-помощь в POI-форме;
- унифицированные действия в формах:
  - черновик,
  - публикация,
  - отмена;
- sticky-summary и preview в формах `poi/routes/products`.

### 12.2. Заказы и операционные процессы

Операторский контур заказов включает:

- список заказов с фильтрами;
- карточку заказа;
- смену статусов;
- быстрые action-кнопки (`подтвердить/отправлен/доставлен`);
- timeline статусов;
- email-уведомления;
- Telegram-уведомления (при активной связке).

### 12.3. Публичный API для витрины

Через `ApiController` опубликованы контракты для `module2`:

- POI / Routes / Products;
- Orders / lookup flow / payment flow;
- analytics events;
- telegram link/status;
- user progress sync/confirmed;
- route complete / reward redeem.

Таким образом, `astrakhan-admin` выполняет роль BFF/API-ядра для пользовательского контура.

### 12.4. Прогресс и награды на сервере

Введен серверный учет:

- snapshot прогресса по пользователю;
- подтвержденные события прохождения маршрутов;
- история списания наград;
- бизнес-правила доступности наград.

Это обеспечивает:

- воспроизводимость расчетов;
- защиту от повторного начисления за один маршрут;
- контролируемость reward-flow.

### 12.5. Интеграции

- SMTP-поток уведомлений;
- Telegram deep-link и уведомления;
- интеграция с модулем тех-аналитики за счет событий и общих данных.

## 13. Полное описание функционала `module3`

`module3` выполняет роль тех-админки и эксплуатационного центра мониторинга.

### 13.1. Аутентификация и роли

- регистрация/логин;
- сессионная авторизация;
- ролевой контроль доступа;
- интерфейсы управления пользователями и ролями.

### 13.2. Базовые метрики

- summary метрики системы;
- daily активность;
- heatmap распределения активности по часам/дням;
- activity API с фильтрацией по роли/пользователю/странице.

### 13.3. Эксплуатационные метрики

Реализовано:

- error rate (по сигналам ошибок в логах),
- latency p50/p95/p99 по реальным логовым данным,
- состояние интеграций (health-представление),
- количество latency-сэмплов.

### 13.4. Бизнес-аналитика и качество данных

- funnel: визит -> просмотр POI -> запуск маршрута -> заказ -> оплата;
- контроль качества данных:
  - заказы без контактов,
  - зависшие статусы,
  - POI без координат/изображений.

### 13.5. Алертинг

Реализован endpoint алертов:

- текущие алерты по пороговым правилам,
- история за 24 часа (почасовой срез).

Это обеспечивает основу для:

- оперативной диагностики,
- построения дашбордов в Grafana,
- формального раздела “эксплуатационная надёжность” в дипломе.

### 15.2. Основные связи для ER-диаграммы

- `roles (1) -> (N) users`
- `users (1) -> (N) visits`
- `users (1) -> (N) logs`
- `points_of_interest (1) -> (N) reviews`
- `routes (N) <-> (N) points_of_interest`  
  (в текущей реализации через `routes.poi_ids`; в перспективе — нормализация в таблицу `route_pois`)
- `orders` логически связан с `users`/`email` и с каталогом `products` через `items_json`
- `user_progress_profiles (1)` на email пользователя
- `route_completion_events (N)` и `reward_redemption_events (N)` связаны с `routes` по `route_id`
- `user_telegram_links` и `telegram_link_tokens` связаны по email/phone/identity данным

### 15.3. Рекомендации для дипломной ER-диаграммы

Показывать ER в двух слоях:

1. **Core ER (бизнес-ядро):**
   - POI, Routes, Products, Orders, Reviews, Feedback
2. **Cross-cutting ER (интеграции и аналитика):**
   - Users/Roles/Visits/Logs, AnalyticsEvents, Telegram links/tokens, Progress/Reward events

Это делает диаграмму читаемой и при этом полной.

## 16. DFD: потоки данных и процессы

### 16.1. Контекстная диаграмма (DFD Level 0)

**Внешние сущности:**

- Пользователь (гость/клиент)
- Сотрудник (оператор/контент-менеджер)
- Тех-администратор
- Telegram API/бот
- SMTP/почтовый сервис
- Платёжный провайдер

**Центральная система:** `Astra-microfront`

**Ключевые потоки:**

- Пользователь -> система: запросы карты, маршрутов, заказа, ЛК
- Система -> пользователь: POI/маршруты/статусы заказа/награды
- Сотрудник -> система: управление контентом и заказами
- Система -> Telegram/SMTP: уведомления
- Система <-> платёжный провайдер: создание и проверка платежей
- Тех-админ -> система: запросы метрик и алертов

### 16.2. DFD Level 1 (рекомендуемые процессы)

#### Процесс P1. Управление контентом

- вход: формы POI/Routes/Products из админки
- хранилища: `points_of_interest`, `routes`, `products`
- выход: публичный API каталога для `module2`

#### Процесс P2. Заказы и доставка

- вход: checkout из `module2`
- хранилище: `orders`
- выход: статус заказа, трекинг, уведомления

#### Процесс P3. Геймификация и прогресс

- вход: route completion, reward redeem, sync snapshot
- хранилища: `user_progress_profiles`, `route_completion_events`, `reward_redemption_events`
- выход: confirmed counters, available rewards

#### Процесс P4. Интеграционные уведомления

- вход: события заказа/привязки
- хранилища: `user_telegram_links`, `telegram_link_tokens`, `news_subscribers`
- выход: сообщения Telegram/email

#### Процесс P5. Аналитика и мониторинг

- вход: `visits`, `logs`, `analytics_events`, `orders`, `points_of_interest`
- выход: metrics/alerts/funnel/data-quality для `module3`
